### Large backup manifests — 0.6.2 (2026-10-19)

- Confirmed the reported installed 0.6.0 run had finished with the 64 MB metadata error. Its partial `Fisiere` directory exists and the manifest is absent. Only status and directory metadata were read; the partial copy, installed plans and agent were not modified. No automatic reconstruction/resumption or new real backup was attempted.
- All plain/archive manifest reads, writes and archive checks now use a consistent 512 MiB limit. Compact JSON is streamed with 256 KiB buffers instead of whole serialized byte vectors. Parsing/writing run on blocking workers. Archive metadata is streamed into SHA-256 and compared by hash and length; restoring archives shares the parsed index with `Arc`. The copy-stage manifest is passed to compression instead of rereading it. Parsed entries and path-validation maps still grow with the source set; no hard RAM cap is claimed.
- A conservative serialized-size budget is checked during source scanning, before file content copying. It includes escaped paths, maximum numeric sizes, checksums and timestamp margin. Over-budget sources stop early and owned VSS cleanup still runs. The 512 MiB limit concerns metadata, not file contents. Legacy version-1 pretty JSON remains supported; old readers retain their old 64 MiB limit.

The archive fixture uses two actual data entries plus valid trailing JSON whitespace, not 180,000 files. Changing only external-manifest whitespace is rejected via hash mismatch.
